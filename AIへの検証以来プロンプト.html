## 第0部　データ収集の前提（最初に必ず読んでください）

**このプロンプトで添付するファイルは、以下の手順で生成されています。**

1. 私は設定JSON（1つ）を使って、シミュレーションを**1回だけ実行**します（試行回数は `config.times`、例:500試行）。
2. その**同じ1回の実行結果**に対して、UI上で「基準年数（N年目）」を10年・15年・17年・20年…のように**複数回指定し直し**、
　そのたびに「CSV①：分岐点分析用サマリー」を出力します。
3. さらに、同じ1回の実行結果から「CSV②：失敗試行」（月次詳細を保持している失敗試行のみ）を1つ出力します。

**したがって、以下を厳守してください。**

- **複数枚あるCSV①（例:10年目用・15年目用・20年目用…）は、互いに独立した別サンプルではありません。
　すべて同じ`config.times`本のモンテカルロ経路を、異なる時点で観測しただけのものです。
　** 例えば500試行×10枚のCSV①があっても、それは「5,000件の独立データ」ではなく「500件の経路を10時点で見た記録」です。
　**枚数分を合算して母数を増やし、統計的検定やAUC算出のサンプルサイズを水増ししないでください。**
- **各CSV①の`試行番号`列は、すべてのCSV①・CSV②で共通のキーです。
　** 同じ`試行番号`は同じモンテカルロ経路を指します。
　したがって、
  - 「ある試行が15年目時点でCAGR何%だったか」と「同じ試行が20年目時点でCAGR何%だったか」を`試行番号`で突合し、
  　**1つの経路の時系列変化を追う**ことは可能です（むしろ推奨します）。
  - 一方で、「15年目CSVでの分析結果」と「20年目CSVでの分析結果」を**別々の独立した検証結果であるかのように**（＝再現性が確認できたかのように）扱わないでください。
  　同じ経路から出た結果なので、両者が似ているのは当然であり、「異なるデータで同じ傾向が出た＝頑健性が高い」という主張の根拠にはできません。
- CSV②（失敗試行）に含まれる試行も、CSV①群と同じ実行由来の試行の一部です。同じ`試行番号`で名寄せできます。
- **「破綻回避のための緊急労働」機能（後述1-2・1-3・1-4節）が有効な設定の場合、労働収入が
  取り崩し圧力を緩和するため、「取り崩し率が高い＝必ず破綻する」という単純な関係が崩れます。
  この機能が有効かどうか（設定JSONの`emergencyLaborConfig.enabled`）を必ず確認し、有効な場合は
  緊急労働収入の有無・多寡を分析対象の変数の1つとして扱ってください。**

**分析・報告時の注意**

- 集計結果を報告する際は、割合（%）だけでなく**必ず該当するn（試行数）を併記**してください。
　特に複数条件を組み合わせて絞り込んだセル（例:「CAGR<0%かつ生活費>◯円」）はnが一桁〜数十件になりやすく、
  見た目の%ほど信頼できない場合があります。
- 「◯%を下回ると破綻率が急上昇する」といった閾値は、**この1回・この設定・この乱数シードでのシミュレーション結果から事後的に見つかった経験的な分岐点**であり、
　一般的・普遍的な「安全ライン」ではありません。
　異なる設定や別の実行（別シード）でも同じ閾値が成立するとは限らない、という留保を必ず添えてください。
- 相関関係を報告する際は、それが**因果関係を示すものではない**ことを明示してください。
　特に「大きな支出イベントの発生月」と「破綻月」が近いといった時間的近接は、単一の経路内で起きた1つの事象にすぎず、
　他の経路のデータ（イベント前の資産水準の分布など）なしに因果を主張しないでください。

## 第1部　添付ファイルの構造説明

### 1-1. シミュレーターの概要

FIRE計画のモンテカルロ・シミュレーターです。数百回の試行を行い、各試行で以下を月次ループで処理します。

- 株価は幾何ブラウン運動（対数正規分布）で変動。銘柄間の相関はコレスキー分解で反映
- 為替はOrnstein-Uhlenbeck過程（平均回帰モデル）で変動
- 毎月、収入から生活費・大きな出費を支払い、不足分は保有資産を売却して補填する
- 資産を売り尽くしても不足額に届かない月を「**破綻**」とし、その試行は失敗と判定する
- 現金／個人向け国債による「暴落時バッファ」戦略を持つ（暴落時はバッファから取り崩す）
- 「マクロ経済レジーム」（5状態のマルコフ連鎖）により、年ごとにインフレ率・株式リターン・
  ボラティリティが変動する（後述）
- **（新機能）「破綻回避のための緊急労働」**：月次の「取り崩し率」が設定したしきい値を
  超えた場合、翌月初から生活費の一定割合を労働収入で賄う（詳細は1-2節・1-5節）

### 1-2. 設定JSONの構造

シミュレーションの入力パラメータ一式です。主なキーは以下のとおりです。

| キー | 内容 |
|---|---|
| `config.birthDate` | 生年月日 |
| `config.cash` | シミュレーション開始時点の現金（円） |
| `config.period` | シミュレーション期間（年） |
| `config.times` | 試行回数 |
| `config.failureDetailLimit` | 月次詳細データを保存する失敗試行の件数上限 |
| `stocks[]` | 保有銘柄。1要素=1口座の1銘柄 |
| `soukan[]` | 銘柄間の相関係数（`A_Meigara` × `B_Meigara` = `keisu`） |
| `tuika[]` | 追加投資（積立）設定 |
| `bigExpense[]` | 特定月に発生する単発の大きな支出 |
| `income[]` | 給与・年金などの収入イベント |
| `tax[]` | 譲渡益課税率（`rate`、%）。デフォルト20.315% |
| `exchangeRate[]` | 為替ペアごとの現在レート・目標レート・ボラティリティ・平均回帰速度 |
| `exchangeRateCorrelations[]` | 通貨ペア間の相関係数 |
| `lifeCostPeriods[]` | 生活費。カテゴリごとに月額（`monthlyAmount`）とインフレ率（`inflationRate`、%） |
| `cashBufferConfig` | 暴落時バッファ設定 |
| `bonds[]` | 手動登録した債券 |
| `inflationModelConfig` | マクロ経済レジームモデルのON/OFFと影響度 |
| `idecoConfig` | iDeCo・退職金の設定 |
| `emergencyLaborConfig` | **（新規）破綻回避のための緊急労働の設定** |

**`stocks[]` の各要素（重要）**

| キー | 内容 |
|---|---|
| `Meigara` | 銘柄名。「ベース銘柄名＜口座種別＞」の形式（例:`SlimSP500＜特定＞`）。口座種別は 特定／旧NISA／成長(新NISA)／積立(新NISA)／iDeCo |
| `Kuchisu` | 保有口数 |
| `Tani` | 基準価額の単位（通常10000） |
| `CurrentValuePerUnit` | 現在の基準価額（`Tani`口あたりの価格） |
| `AveragePrice` | 平均取得価額（`Tani`口あたり） |
| `Return` | 期待年率リターン（%） |
| `Volatility` | 年率ボラティリティ（%） |
| `ExchangeRate` | 参照する為替ペア（円建てのみなら空） |
| `AnomalyFilterEligible` | 「長期平均年率マイナスは歴史的に考えにくい」とみなす銘柄か |

**評価額の計算式**：`評価額(円) = Kuchisu ÷ Tani × CurrentValuePerUnit`
（例: `Kuchisu=23254834, Tani=10000, CurrentValuePerUnit=44308` → 約1億304万円）
**必ずこの式で計算してください。`Kuchisu` をそのまま円として扱わないでください。**

**`cashBufferConfig` の各キー**

| キー | 内容 |
|---|---|
| `enabled` / `useJgbBuffer` | バッファ機能のON/OFF、国債バッファを使うか |
| `cashBufferYears` | バッファ目標額（生活費の何年分か） |
| `crashThresholdPct` | 高値からの下落率がこの%を超えたら「暴落モード(CRISIS)」に入る |
| `recoveryThresholdPct` | ここまで回復したら通常モードに戻る |
| `jgbCouponRate` | 変動10年国債の想定クーポン率（%） |
| `jgbStartYearMonth` | 国債バッファの購入開始年月 |

**`idecoConfig` の各キー**

| キー | 内容 |
|---|---|
| `enabled` | iDeCo機能のON/OFF |
| `startYearMonth` | iDeCo拠出開始年月 |
| `receiveYearMonth` | iDeCo受給予定年月 |
| `severanceAmount` / `severanceYearMonth` | 会社の退職金額と受取年月 |
| `companyServiceYears` | 会社の勤続年数（退職所得控除の計算に使用） |

iDeCoは原則、受給可能年齢（生年月日と拠出開始年月から決まる60〜65歳）まで引き出せません。
ただし本シミュレーターでは、**受給可能年齢に達していれば、他に売る資産が尽きた段階で
iDeCoを繰り上げて全額一括取り崩す**ロジックが入っています。受給可能年齢前に資産が尽きた
場合は取り崩せず、そのまま破綻します。

**`emergencyLaborConfig` の各キー（新規）**

| キー | 内容 |
|---|---|
| `enabled` | 機能のON/OFF（デフォルトOFF） |
| `limitAge` | 緊急労働を発動できる限界年齢（歳）。この年齢を超えた翌月以降は発動しない |
| `tiers[]` | 3段階のしきい値設定。各要素は`{ thresholdPct, laborPct }` |

`tiers`の各段階は「取り崩し率が`thresholdPct`（%）以上のとき、生活費の`laborPct`（%）を
労働で稼ぐ」ことを意味します。3段階は`thresholdPct`が小さい順（下の段階に進むほど、
対応する`laborPct`も大きくなる想定）に並んでいます。`thresholdPct`または`laborPct`が
`null`（空欄）の段階は「設定しない」ことを意味し、発動しません。

**「取り崩し率」の定義（本シミュレーター内部での計算式）**：
`取り崩し率(%) = 当月の月次生活費（大きな出費は含めない）× 12 ÷ 当月末の総資産 × 100`

「4%ルール」と同じ考え方の、資産水準そのものに対する構造的な比率です。その月に
たまたま現金が足りた／足りなかったといった単月の資金繰りの結果（実際の取り崩し額）
には依存しません。

3段階のしきい値のうち、その月の取り崩し率が上回っているもののうち最もしきい値が高い
（＝最も深刻な）段階の`laborPct`が採用され、**その判定の翌月から**、その月の生活費水準に
`laborPct`を掛けた金額が収入に追加されます（「発動の翌月初から給料が入る」仕様）。
取り崩し率は資産水準のみで決まり当月の労働収入の影響を受けないため、条件を満たしている
間（＝資産が生活費に対して十分な水準に回復するまで）は毎月継続して発動します。
既に破綻が確定した試行では、それ以降は判定されません（労働の意味がないため）。

**分析上の注意**：この機能が有効な場合、取り崩し率が高い試行ほど労働収入が発生し
（＝資産からの追加取り崩しが抑制される）ため、「取り崩し率が高いほど破綻しやすい」
という単純な相関が弱まったり、非線形になったりする可能性があります。`enabled`が`true`か
どうかを必ず確認し、`true`の場合はタスク1で緊急労働収入も説明変数として分析してください。

**マクロ経済レジーム（`inflationModelConfig.enabled` が true のとき有効）**

年1回、以下5状態を確率的に遷移します。各状態がその年のインフレ率・株式リターン・
ボラティリティに影響します（`regimeIntensity` が `weak`/`normal`/`strong` で影響度を調整）。

| レジーム | 意味 | インフレ加算 | 株式リターン加算 | ボラ倍率 |
|---|---|---|---|---|
| NORMAL | 通常 | 0.0pt | 0.0pt | ×1.0 |
| OVERHEAT | 過熱（マイルドインフレ×株高） | +1.5pt | +3.0pt | ×1.0 |
| TIGHTENING | 引き締め（高インフレ×株安） | +3.0pt | -6.0pt | ×1.3 |
| STAGFLATION | スタグフレーション | +5.0pt | -12.0pt | ×1.6 |
| GOLDILOCKS | 好況（低インフレ×株高） | -1.0pt | +5.0pt | ×0.8 |

TIGHTENING と STAGFLATION を「**悪性レジーム**」と呼びます（CSVの列名に登場します）。
※上表は `regimeIntensity` が `normal` のときの基準値です。`weak` は0.5倍、`strong` は1.6倍に
スケールします（ボラ倍率は1.0からの乖離幅をスケール）。

### 1-3. CSV①「分岐点分析用サマリー」（`FIRE_分岐点分析_N年目_日時.csv`、複数枚あり）

**1行 = 1試行**。全試行（成功・失敗の両方）が含まれます。**分析の主役はこのファイルです。**
ファイル名とヘッダの「N年目」は、私がUIで指定した基準年数です。**同じ実行から異なるN年目で
出力した複数枚を渡すことがあります。第0部の注意を必ず踏まえてください。**

| 列名 | 内容 |
|---|---|
| `試行番号` | 1始まりの試行番号（全CSVで共通のキー。経路の突合に使用可） |
| `最終結果` | `成功` または `失敗` |
| `破綻月Index` | 破綻した月の通し番号（0始まり）。成功試行は空欄 |
| `最終総資産額` | シミュレーション終了時点の総資産（円） |
| `N年目時点_月次生活費（インフレ適用後）` | N年目時点の1ヶ月の生活費（円） |
| `N年目時点_緊急労働月収（円）`（新規） | N年目時点の月に、緊急労働で得ていた収入額（円）。緊急労働が発動していなければ0 |
| `N年目までの緊急労働収入累計（円）`（新規） | 開始時点からN年目までに、緊急労働で得た収入の累計額（円） |
| `N年目時点_CRISIS滞在月数` | 開始からN年目までの間に暴落モードだった月数 |
| `N年目までの悪性レジーム(TIGHTENING/STAGFLATION)発生年数` | 悪性レジームが1ヶ月でも発生した年の数 |
| `【銘柄ベース名】_累積CAGR(N年目まで)%` | 開始からN年目までの、その銘柄の累積平均年率（%）。銘柄数だけ列がある |
| `【為替ペア】_累積CAGR(N年目まで)%` | 同上、為替ペアごと |

**注意**：`CRISIS滞在月数` と `悪性レジーム発生年数` の2列は、月次詳細データを保持している
試行でしか計算できないため、**多くの行が空欄**になります。この2列だけは
「値が入っている行のみ」を母数として分析し、**空欄を0として扱わないでください**。
一方、緊急労働関連の2列は全試行分の軽量記録から算出されるため空欄にはなりません
（緊急労働が無効・未発動の試行は単純に0円になります）。

### 1-4. CSV②「失敗試行」（`FIRE_失敗試行_日時.csv`）／ CSV③「単一試行」

**1行 = 1試行の1ヶ月分**。②は破綻した試行のうち詳細を保持しているものだけ、③は指定した1試行分です。
**②・③に含まれる試行も、CSV①群と同じ1回の実行から出たものです。`試行番号`で名寄せできます。**

| 列名 | 内容 |
|---|---|
| `試行番号` | 試行番号 |
| `破綻月Index` | その試行が破綻した月の通し番号 |
| `年月` | **シミュレーション開始からの経過**。「0年1月」が開始1ヶ月目、「18年3月」は開始から18年経過後の3ヶ月目。**西暦ではありません** |
| `総資産` / `現金` | その月末の総資産・現金（円） |
| `出費` | その月の支出（生活費＋大きな出費） |
| `収入` | その月の収入（給与等＋配当・分配金＋国債バッファ利息＋緊急労働収入） |
| `追加投資` | その月の積立額 |
| `ideco収入` | iDeCo・退職金の一括受給額（手取り） |
| `緊急労働収入`（新規） | その月に、破綻回避のための緊急労働で得ていた収入額（円）。上記`収入`列にはこの金額も合算済み |
| `税金` | その月の税金合計 |
| `isFailure` | `TRUE`=破綻済み、`FALSE`=破綻前 |
| `国債バッファ評価額` / `国債バッファ口数` / `国債バッファ当月利息` / `国債バッファ購入額` | 国債バッファの状況 |
| `【銘柄名】_評価額` / `_口数` / `_基準価額(1Taniあたり)` / `_平均取得価額(1Taniあたり)` / `_月次リターン率%` | 銘柄ごとに5列 |
| `【為替ペア】_レート` / `_変動率%` | 為替ペアごとに2列 |

**重要な注意**
- **破綻した月以降の行は、総資産・現金・投資資産・国債バッファがすべて 0 に固定されます**。
  これは仕様（破綻後の表示混乱を防ぐため）です。**破綻後の行を「資産推移のデータ」として
  分析対象に含めないでください。** 分析すべきは `isFailure=FALSE` の期間と、破綻した瞬間の行です。
- 破綻後も `収入`（年金等）や `出費` の列には値が入り続けます。これは「破綻しなければ
  発生していたはずの金額」であり、実際には支払えていません。緊急労働も、既に破綻が確定した
  試行ではそれ以降判定されない（＝発動しない）ため、破綻後の`緊急労働収入`列は常に0です。

### 1-5. 緊急労働の判定タイミングと因果関係の注意（新規）

緊急労働は「当月末の取り崩し率」を見て「翌月の収入」を決めるという、1ヶ月のラグを
持った仕組みです。そのため、
- ある月の取り崩し率が高くても、それが**翌月**の収入増加として現れるまでは資産の
  取り崩しは緩和されません。取り崩し率の悪化と収入増加のタイミングが1ヶ月ずれる点に
  注意してください。
- 「緊急労働収入が多い試行ほど成功しやすい／失敗しやすい」という単純な相関だけを見て
  因果を主張しないでください。緊急労働はもともと取り崩し率が高い（＝資産状況が厳しい）
  試行でこそ多く発動するため、「緊急労働収入が多い＝資産状況が厳しかった結果」という
  逆方向の解釈も同時に成り立ちます。

## 第2部　分析してほしいこと

### タスク1　破綻の要因分析

添付したCSV①（分岐点分析用サマリー、複数枚の場合あり）を統計的に分析し、以下を明らかにしてください。
**第0部の前提（複数枚は独立サンプルではない）を踏まえて分析してください。**

1. **成功率**と、破綻した試行の**破綻時期の分布**（何年目に破綻が集中しているか）
2. 成功群と失敗群を比較し、**どの変数が成否を最も強く分けているか**を特定してください。
   - 各説明変数（銘柄別CAGR、為替CAGR、N年目時点の月次生活費、**N年目までの緊急労働収入累計**、
     CRISIS滞在月数、悪性レジーム年数）について、成功群・失敗群の平均／中央値／分布を比較する
   - 可能なら、成否を目的変数とした**ロジスティック回帰や決定木**で寄与度を定量化する
   - **CSV①が複数枚ある場合、各枚は同一試行群を別時点で見たものなので、個別に集計・報告し、
     「別々の独立した検証結果」であるかのように扱わないでください。**
   - `emergencyLaborConfig.enabled`が`true`の場合、緊急労働収入の多寡が成否の分岐にどう
     関わっているか（1-5節の注意を踏まえ、因果ではなく相関として）も報告してください。
3. **「この水準を下回ると破綻確率が急に跳ね上がる」という閾値（分岐点）**を、主要な変数ごとに
   数値で特定してください。**その際、該当するnも必ず併記してください。**
   例：「N年目時点のS&P500累積CAGRが◯%を下回ると、破綻率が△%から□%に跳ね上がる（n=◯）」
4. **複数条件の組み合わせ**も検討してください。**nが小さくなりやすいので、各セルのnを必ず明示してください。**
   例：「CAGRが◯%未満 **かつ** 月次生活費が△円超」の場合の破綻率（n=◯）
5. CSV②がある場合は、破綻に至る典型的な経路（資産が減り始めてから破綻までの年数、
   どの資産から先に枯渇するか、バッファがいつ尽きるか、**緊急労働が発動していたか・
   発動していたにも関わらず破綻に至ったか**）を記述してください。
   **時間的に近接して起きた2つの事象（例:イベント発生と破綻）を、それだけで因果関係として
   断定しないでください。**

### タスク2　破綻を防ぐ具体的な行動ルールの提案

タスク1で特定した閾値をもとに、**実行可能な行動ルールを最低8個**提案してください。

**必ず、以下の形式の「条件付きルール」で書いてください。**
抽象的な助言（「支出を見直しましょう」等）は不要です。**具体的な数値**を入れてください。

> 【ルール例】
> - 資産が◯◯◯◯万円を下回った場合、自宅購入イベントの予算を△△△△万円に減額する（または◯年延期する）
> - 資産が◯◯◯◯万円を下回った年は、その年の支出の△△%をアルバイト収入で賄う（月額◯◯万円相当）
> - 65歳到達時点の資産が◯◯◯◯万円未満なら、ポートフォリオを期待リターン△%・ボラティリティ□%以下の構成に切り替える
> - 高値からの下落率が◯%を超えた年は、生活費を△△%（月◯万円）カットする
> - 国債バッファの目標を生活費◯年分に変更する

**カバーしてほしい観点**（この設定データから読み取れるものだけで結構です）
1. **大きな支出（`bigExpense`）**：金額・時期の見直し。「いくらまでなら安全か」「何年遅らせれば安全か」
2. **支出のガードレール**：資産水準に応じた生活費の可変ルール（ガードレール戦略）
3. **収入の追加**：アルバイト・副業。「いつ・いくら稼げば破綻を防げるか」の最小ライン
4. **ポートフォリオ構成**：期待リターンとボラティリティのトレードオフ。分散・債券比率・
   低ボラ資産への切り替えタイミング
5. **取り崩し戦略**：売却順序、暴落時バッファ（`cashBufferConfig`）のパラメータ調整
6. **iDeCo・退職金**：受給タイミングの最適化（受給可能年齢・退職所得控除を踏まえて）
7. **為替リスク**：円建て資産の比率
8. **時間的な猶予**：リタイア時期を遅らせる／積立を延長する効果
9. **（新規）緊急労働の発動条件の校正**：タスク1で特定した「取り崩し率と破綻確率の分岐点」を
   踏まえ、`emergencyLaborConfig.tiers`の`thresholdPct`（〇・●・▲）・`laborPct`（□・■・◆）を
   どう設定すれば効果的か。既に緊急労働を有効にして実行した結果であれば、設定した
   しきい値・労働割合が適切だったか（発動が遅すぎた／労働割合が不足していた等）も評価してください

各ルールについて、以下を必ず記載してください。

- **発動条件**（具体的な金額・年齢・下落率などの数値）
- **とるべき行動**（具体的な金額・割合）
- **なぜ効くのか**（タスク1の分析結果のどの数字を根拠にしているか。該当するnも明記）
- **副作用・トレードオフ**（生活の質の低下、期待リターンの低下など）
- **優先度**（高／中／低。効果の大きさと実行の容易さで判断）
- **この閾値がこの1回のシミュレーション結果に固有のものである可能性**（再検証が必要かどうか）

### タスク3　検証方法の設計
